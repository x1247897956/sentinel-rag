# 关键取舍（为什么这么做、否掉了什么）

> 每条都写「当时的备选方案」和「为什么没选」，因为这才是面试官会追问的部分。

## 1. 为什么把中文分词放在应用层，而不是装 `zhparser` / `pg_jieba`

**做法**：入库前用 `jieba.lcut_for_search` 分词，结果存 `chunks.tokens` 一列，
再对其建 `tsvector`（`to_tsvector('simple', tokens)`）+ GIN 索引。

**否掉的方案**：在 PostgreSQL 里装中文分词扩展。

**原因**：扩展需要自编译镜像，本地与容器里的编译产物不一致，换台机器可能就装不上；
提到应用层后，检索链路和部署都变成确定的，代价只是多存一列。
`sql/init.sql` 里因此只用 `simple` 配置，不依赖任何第三方扩展（除 `vector`）。

**可验证**：`make smoke` 里的 `probe` 会同时打印「整句当一个 token」和「jieba 预分词」
两种做法的命中数——前者恒为 0，后者上千（见 `docs/eval-report.md` §4.4）。

## 2. 为什么用 RRF，又为什么最终给它加了「名次权重」

**RRF 的部分**：向量余弦相似度（0~1）与 `ts_rank`（无界）量纲不可比，
分数加权求和需要归一化，而归一化系数要逐语料标定；RRF 只用名次，跨查询稳。

**加权的原因**：本项目的语料是**英文为主**（CVE/GHSA/ATT&CK 的正文），
查询是**中文**，向量一路的 `recall@5` 只有 0.31，而全文一路有 0.85。
等权 RRF 会让「向量排第 1、但全文完全没命中」的噪声候选，压过「全文排第 25」的
真实命中（1/61 > 1/85）。因此给全文一路更高的名次权重（3 : 1）。

**注意**：权重是**每一路一个常数**，不是每条候选一个分数——这与 RRF「只用名次」的
核心思想不冲突。权重来自评测集上的对照实验，不是随手填的。

## 3. 重排：为什么最终**没有**用 cross-encoder，也没有用 LLM 重排

三种重排后端都实现并测过（代码都在，可切换）：

| 后端 | 结果 | 结论 |
| --- | --- | --- |
| `cross_encoder`（`bge-reranker-base`） | 同一问题下 30 个候选的分数几乎全为 0.5~0.62，排序与融合结果脱节；CPU 上 30 候选约 9s | **不可用**：该权重对本语料（中文问题 + 英文正文）区分度不足 |
| `llm`（DeepSeek 逐条打分） | 打分可用，但单问 2~18s；且打分偏低时会把本可回答的问题判成拒答 | 成本与延迟不划算 |
| `score_fusion`（两路**原始**分数按固定量纲加权，不做池内归一化） | 确定性、毫秒级（P50 2 ms），MRR 优于等权融合 | **最终采用** |

**诚实结论**：本项目的语料是混合语言，通用中文 cross-encoder 在这里没有带来收益。
真正要修的是「embedding 与 reranker 都要选多语种/英文域模型」——这是已知限制之一，
`docs/eval-report.md` §7 有记录。

## 4. 分块：为什么按 section + 行/句原子单元，而不是固定字符数

**做法**：先按 `## 小标题` 切 section，再在 section 内以「行 → 句 → 字符窗口」的
优先级打包到目标长度（~420 token），重叠 ~80 token。

**否掉的方案**：固定 512 字符滑窗。

**原因**：安全语料的语义单元差异极大——CVE 的「受影响版本区间」是若干行
`version=5.6.0 < 5.6.3`，一条版本区间被切开就会答错影响面；OWASP 的正文是长段落，
按字符切会把一句话拦腰截断。**版本区间不切散**由单测 `test_version_range_not_split` 守着。

## 5. 为什么评测要分「四组配置」而不是只报最终数字

只报最终配置时，「混合检索与重排到底有没有用」只能靠嘴说。四组单变量对照
（A 纯向量 / B 纯全文 / C 混合 / D 混合+重排）把每一步的增量拆开，
**并且允许出现"某一组不如预期"的结论**——本项目的 B > C 就是这样被发现的，
比编一个好看的单调性更有价值。

## 6. 为什么把模型回答「冻结」进仓库

CI 里放长期 LLM API key 不是好做法。因此生成阶段只在本地跑一次，
把每条回答连同 `citations` / `allowed_ids` / `refused` / `gold_chunk_ids` 一起冻结到
`eval/snapshot/`，CI 用这些**完整证据字段**确定性重算引用命中率、引用幻觉率、
拒答正确率。任何人可以逐条复核，且不需要密钥。

## 7. 为什么 embedding 缓存必须**无损**写盘（一个真实的复现性坑）

**做法**：入库前把「模型名 + 全部语料文档的 `content_hash`」哈希成缓存键，把编码结果写成
`data/cache/embeddings_<key>.jsonl`；命中就复用，未命中才编码（2619 chunk 冷编码约 410 s，
热缓存全量重建 6.8 s）。写盘时直接 `json.dumps(v)`，**不做任何 round**。

**踩过的坑（这版修掉的）**：缓存曾写成 `round(x, 6)`，而写进 PostgreSQL 时
`_vec_literal` 按 `%.7f` 格式化。于是：

- **缓存未命中**：模型原始 float → `%.7f` → 7 位小数；
- **缓存命中**：6 位小数 → `%.7f` → 只保留 6 位。

两条路径写进库的向量在第 6/7 位小数上不同。pgvector 的 HNSW 是**近似**检索，
这点差异足以让个别「近似并列」的候选换序，于是**同一条命令、同一份语料，跑出不同的
`recall`/`MRR`**（实测纯向量 `recall@5` 0.3108 vs 0.2973，差一整道题）。

**修法**：把量化点收敛到 `_vec_literal` **一处**，缓存无损落盘。

**验证**（不靠"看起来一样"，靠哈希）：冷缓存全量重建与热缓存重建之后，
`md5(string_agg(chunk_id || embedding::text, '|' ORDER BY chunk_id))` 两次都是
`bd89bb7f58dd310be3f6913e21357e2b`；两次独立检索评测的四组指标完全一致（见
`docs/eval-report.md` §9）。

**留一条更一般的教训**：做检索评测时，「确定性」不只是"关掉 temperature"——
**索引构建路径上的任何量化/近似都可能让指标漂移**，而漂移量恰好和"改动效果"同量级，
会让人把噪声当成收益。

## 8. 已知未做（主动声明边界）

- 未做 MCP 工具层、多轮会话、护栏（方案里的 P2/P3）；
- 未做向量库横向选型对比；也**没有**把 HNSW 换成精确（暴力）检索：千级 chunk 下精确检索
  代价可接受，且能去掉近似检索带来的抖动，**本轮没做**（见 §7 与 `docs/eval-report.md` §10-7）。
- 未做大规模吞吐压测：真实边界是**单机 / 千级 chunk / 单租户**。
